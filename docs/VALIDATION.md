# 当前扩容验收

当前代码支持维度 1–2、整数 0–100。超过 9 的输入使用固定大牌堆。扩容测量与验收记录独立存放在 `evidence/expanded/`，结果说明见 [大数值 2×2 实测结果](EXPANDED_RESULTS.md)。本页下方的旧性能数据保留为历史记录，不绑定到扩容后的新程序。

扩容后的验收包括 12 组两版极速对比（每版每例 1 次预热＋3 次实测）、两版各 127 个原引擎回归与 21 个输入/记录回归、16 个扩容故障/输入边界/控制/重播用例，以及独立版本同时运行检查。最终通过情况以各目录 summary.json 与 `evidence/frozen/expanded-v1-manifest.json` 为准。

# 双版本验证记录

日期：2026-11-03。当前交付分别为原始无优化版 `Baseline` 和优化版 `Optimized`，均为原生 Windows Release 程序。后台验证未使用 Computer Use。

## 当前两版

每版分别通过 127 个引擎用例和 21 个输入/记录用例，共 **296 个用例**。覆盖全部 a,b=0…9、矩阵边界、固定种子随机矩形矩阵、暂停/单步、三种播放速度、故障停机、无效输入以及同版记录重播。

原始版另外与先前冻结记录逐项比较：已有样例对应的初始局面、牌堆、动作轨迹、最终玩家状态和 C 保持一致。B=0 仍完整执行出杀、救援、放逐。优化版固定使用跳过零项及自动选择计算方向。

`test_isolation.py` 同时启动两个程序，共用同一个启动目录和输入：

- 两个进程确实重叠运行并各自正确完成。
- 两者的配置路径位于各自程序目录，且文件名不同；启动目录中的 config.ini 哨兵保持原样。
- 使用实际 NativeServerSocket 路径同时监听，不同的系统分配端口均成功绑定。
- 结果分别写入独立文件，记录的 edition 正确。
- 两个程序都拒绝请求另一版算法的输入。

构建脚本支持两个目标顺序构建并强制独立链接。重复构建之后再次检查版本隔离和示例，避免复用缓存时把错误程序复制到另一个文件名。

数据位于 `evidence/versions/baseline/`、`evidence/versions/optimized/`、`evidence/versions/isolation/`。

通用极速对比入口 `scripts/compare.py` 已运行验证：强制覆盖输入中的播放速度及算法选择，两版共用同一份规范化输入，分别调用各自 exe；零工作量时不会除零，错误输入会清除同目录旧成功报告。固定样例 HTML 与统计 JSON 已生成，报告链接原始统计，记录程序和输入 SHA256。整个过程不操作桌面。

## 当前双版本性能

现采用预先固定的 **96 组不同矩阵输入**，覆盖全部 8 种合法尺寸，含 40 组完整 2×2 乘法；55 组来自双方均无零的稠密分布。两个程序均为极速档，每例每版预热一次、实测十次，共 **2,112 次原生程序调用，全部结果正确**。每轮交替版本先后顺序，串行运行。

按每例“准备＋结算”中位数之比、以 ±5% 为展示区间：**48 组更快、46 组接近、2 组更慢**。此区间不表示统计显著性。稠密均匀 1–9 组的倍数中位数为 1.04×，左大右小组为 4.39×；全 9 用例约 1.00×。

明确退化案例：`A=[[8,7],[9,9]], B=[[7],[8]]`，两版 C 均为 `[[112],[135]]`。优化后出杀由 33 减至 30，但准备＋结算由 205.97 ms 增至 297.09 ms，约慢 44%。另一较慢用例双方均零出牌，准备阶段差约 0.17 ms；不把这种小差异解释为已证实的算法退化。

全部输入、分组统计和逐次数据在 `evidence/versions/suite-v1/`；分析见 [多测试集实测结果](TEST_SUITE_RESULTS.md)。`scripts/verify_suite.py` 独立检查全部 2,112 份原生记录、结果武将手牌、救援后体力、摸牌轨迹、汇总数值、输入/方法哈希以及 97 份 HTML 的链接，通过记录为 `integrity.json`。测试生成器可按固定种子逐字节重现输入；单例运行、完整报告续跑和拒绝变更测量参数已验证，见 `evidence/suite-tooling/`。

本轮只扩展测试和报告，两个原生程序未改动。历史单位矩阵演示保留在 `evidence/versions/benchmark/`，该单例的 13.77× 引擎倍数不再作为整体性能结论。并行隔离检查与性能测量分别执行。

两版最终 GUI 外观未做人工复验；普通对局完整回归及另一台干净 Windows 机器的兼容验收仍未执行。后台隔离检查不替代这些项目。

# 历史组合版验证记录（保留供比较）


日期：2026-11-03。本机 Windows，Qt 5.5.1 / MinGW 4.9.2 32 位 Release。全部数值来自打包后 `SanguoshaGEMM.exe` 的真实 QSanguosha 引擎，测试脚本中的整数乘法仅用于独立核验。

## 已通过

`scripts/test_engine.py`：165 个后台用例，原始输入、记录与日志在 `evidence/engine/`。

- 全部 100 个标量组合 a,b=0…9，逐步检查曹丕存活且恢复到 1 血、手牌结果为 ab。
- 指定示例 `[[4,5],[6,3]]`，12 杀、12 次急救、12 次放逐、共摸 18 张。
- 三种算法分别测试全 9、单位矩阵、零矩阵，以及固定种子随机矩形输入；全 9 结果的四个位置均为 162 张手牌。
- 暂停时停留在第 0 步；两次单步各完成一次完整结算；随后恢复自动播放完成剩余任务。
- 同一标量在正常、加速、极速三档结果一致。
- 无救援牌、空牌堆、攻击距离不足均停止，输出失败及原因，未误报成功。
- 每个用例在进入 GEMM 前检查普通模式抽牌结果不含扩展计算牌。

`scripts/test_records.py`：25 个后台用例，原始记录在 `evidence/records/`。

- 19 个错误输入：不合法 JSON、错误对象类型、空矩阵、维度/行宽/乘法尺寸不符、负数、小数、超界、布尔/字符串/null、未知算法或速度等。返回非零并输出错误 JSON，不输出成功结果。
- 每个算法运行一次，再把完整记录作为输入重跑。初始武将/牌堆、逐步动作和用牌、最终玩家状态、C 与操作统计完全一致；只排除时间等非确定字段。
- 核验每步实际救援牌及摸牌 ID 数量，核验进程 CPU 时间、内存统计有值。

合计 190 个测试调用。没有用软件模拟替身代替原引擎，也没有把参考乘法答案写入结果手牌。

另将便携 ZIP 解压到独立目录，不携带之前的 config.ini，后台启动并运行指定示例成功。结果记录为 `evidence/portable-smoke.json`；这是本机解压启动检查，不是另一台机器的兼容性验收。
